# Spanner Objects and Their Nuances

How Atlas models Spanner objects, what Spanner allows to change in place, and the cases where Atlas's plan
differs from what a hand-written migration would do. The full attribute reference is
https://atlasgo.io/hcl/spanner. HCL syntax is in `references/hcl.md`, and running the changes is in
`references/migrations.md`. The Spanner driver needs `atlas login`. If `atlas whoami` shows no login,
ask the user to run `atlas login`; a user without an account can start a free trial with it.

## What Atlas Manages

Atlas inspects and plans tables, columns with their defaults, generated expressions, and options,
primary keys, `INTERLEAVE IN PARENT`, secondary indexes, search and vector indexes, foreign keys, checks,
row deletion policies, sequences, views, change streams, named schemas, property graphs, locality groups,
placements, and roles and grants (https://atlasgo.io/hcl/spanner).

## What Atlas Leaves Out

These were checked with the emulator as dev database. Each is planned without an error, so a plan that
looks complete can still miss them:

| Object or clause | What happens | What to do |
|------------------|--------------|------------|
| Identity columns, `GENERATED BY DEFAULT AS IDENTITY` | Planned as a plain `INT64 NOT NULL`: inserts that omit the key fail | Use a named sequence (Sequences, below) |
| A table without a primary key | Planned with a visible `rowid INT64 NOT NULL` key and no generator | Declare a primary key |
| `NOT ENFORCED` foreign keys | Planned as enforced foreign keys, which validate every row | Create them by hand (Foreign Keys, below) |
| Interleaved indexes, `CREATE INDEX ... , INTERLEAVE IN Parent` | Planned as global indexes | Create them by hand in a migration file |
| `INTERLEAVE IN` tables, without `PARENT` | Inspection fails: `Scan error on column index 3, name "on_delete_action": converting NULL to string is unsupported` | Use `INTERLEAVE IN PARENT` (Interleaving, below) |
| Adding or removing interleaving on an existing table | The plan reports no changes | Interleaving is permanent: create a new table and copy the rows |
| Database options, `ALTER DATABASE ... SET OPTIONS` | Left out of plans | Write them in a migration file (`references/migrations.md`) |
| Synonyms, `ADD SYNONYM` | Not inspected or planned | Manage them by hand (`references/migrations.md`, Renames) |
| Proto bundles | Atlas cannot send the descriptor set Spanner needs | Update the bundle with `gcloud` first (https://atlasgo.io/guides/spanner/proto-columns) |
| A sequence in a named schema | Planning fails: `Drop sequence "OrderSeq": ... Sequence not found` | Keep sequences in the default schema |
| Vector index options, locality group options, and placements, in a SQL schema | Lost on an emulator dev database | Declare them in HCL (`references/hcl.md`) |

Other changes reach the plan in a form Spanner rejects, or that loses data:

| Change | What Atlas plans | What to do |
|--------|------------------|------------|
| Remove a column and the index, `STORING` list, or view that uses it | `DROP COLUMN` first, which fails: `Cannot drop column ... because it is used by index ...`, or `on which there are dependent views` | Drop or replace the dependent object first (`references/migrations.md`, Dependent Objects) |
| Change the expression of an indexed stored generated column | `DROP COLUMN` and `ADD COLUMN`, which fails on the index | Drop the index, replace the column, then recreate the index |
| Change a change stream's options or watched columns | `DROP CHANGE STREAM` and `CREATE CHANGE STREAM`, which deletes its change records | Write `ALTER CHANGE STREAM` by hand (Change Streams, below) |
| Rename a table | A drop and a create, which loses the rows (`DS102`) | Write the rename by hand (`references/migrations.md`, Renames) |

## Keys and Hotspots

Spanner splits a table by primary key ranges. Keys that grow with every insert, such as a timestamp or an
id the application increments, send all new rows to the last split, which caps write throughput
(https://docs.cloud.google.com/spanner/docs/schema-design#primary-key-prevent-hotspots). Pick one of:

- A UUID version 4: `STRING(36) DEFAULT (GENERATE_UUID())`, or the `UUID` type with
  `DEFAULT (NEW_UUID())`. Not version 1, which puts the timestamp in the high bits.
- A bit-reversed sequence for `INT64` keys (Sequences, below).
- A hash or shard prefix, a swapped key order, or a descending timestamp key, from the same page.

The same applies to indexes: do not create a non-interleaved index on a frequently written column whose
value only grows, and do not lead a key or index with a commit timestamp column
(https://docs.cloud.google.com/spanner/docs/commit-timestamp#keys-indexes). The custom rules in
`references/custom-rules.md` enforce this.

- Primary keys cannot change after the table exists. A changed key fails planning with
  `spanner: the keys of a table cannot change after table creation`. Create a new table, copy the rows,
  and switch the application over.
- Keys hold up to 16 columns, including those inherited from parent tables, and 8 KiB
  (https://docs.cloud.google.com/spanner/quotas#schema-limits). `FLOAT32`, `ARRAY`, and `JSON` columns
  cannot be keys or index keys
  (https://docs.cloud.google.com/spanner/docs/reference/standard-sql/data-types#valid_key_column_types).
- Descending key parts plan only from SQL schemas (`references/hcl.md`, Keys and Interleaving).

## Interleaving

`INTERLEAVE IN PARENT` stores child rows with their parent row: the parent's primary key must lead the
child's key, a child row needs its parent row, and `ON DELETE CASCADE` deletes children with the parent.
Tables nest up to 7 levels
(https://docs.cloud.google.com/spanner/docs/schema-and-data-model#create-interleaved-tables).

- Interleaving is permanent: Spanner cannot interleave an existing table or remove its interleaving, and
  Atlas then reports no changes. Create a new table and copy the rows.
- An `ON DELETE` change is planned in place:
  `ALTER TABLE Albums SET INTERLEAVE IN PARENT Singers ON DELETE CASCADE`.
- Atlas cannot inspect a database that has a table interleaved with `INTERLEAVE IN`, without
  `PARENT`, so every command that reads the database fails. Convert the table once, outside Atlas:

  ```bash
  gcloud spanner databases ddl update <database> --instance=<instance> \
    --ddl='ALTER TABLE Albums SET INTERLEAVE IN PARENT Singers'
  ```

  The conversion fails when child rows have no parent row. Going from `INTERLEAVE IN` to
  `ON DELETE CASCADE` takes two statements: `SET INTERLEAVE IN PARENT`, then `SET ON DELETE CASCADE`
  (https://docs.cloud.google.com/spanner/docs/reference/standard-sql/data-definition-language#alter_table).
- A key column that interleaved children inherit cannot change, not even its length: planning fails with
  `Requested change to key column Singers.SingerId could not be made`.
- A table with a row deletion policy needs `ON DELETE CASCADE` on all its interleaved children
  (Row Deletion Policies, below).
- Google recommends either a foreign key or interleaving between two tables, not both
  (https://docs.cloud.google.com/spanner/docs/foreign-keys/overview).

## Columns and Types

- Spanner changes a column's type in place only between `STRING` and `BYTES`, to another length, from
  `INT64` to an `ENUM`, and between proto types
  (https://docs.cloud.google.com/spanner/docs/schema-updates#supported-updates). Atlas plans any other
  change as `ALTER COLUMN`, and planning fails with
  ``Cannot change type of column `Age` from `INT64` to `STRING` ``. Add a new column, backfill it, switch
  the application, and drop the old column in a later migration.
- A shorter `STRING(n)` or `BYTES(n)` checks every row, and fails on a longer value:
  `Reducing the length of column Nick to 5 is not allowed because it has a value of length 8`. Lint
  does not report it.
- A new `NOT NULL` column on an existing table needs a `DEFAULT`, or a stored generated expression.
  Without one, planning fails with `Cannot add NOT NULL column Users.Status to existing table Users`. An
  `ARRAY` column can be `NOT NULL` only when its table is created.
- Making a column `NOT NULL` checks every row, and fails on `NULL` rows even when the column has a
  `DEFAULT`: `ALTER COLUMN` does not backfill. Spanner rejects new `NULL` writes as soon as the change
  starts (https://docs.cloud.google.com/spanner/docs/schema-updates#updates-that-require-validation).
  Lint reports it as `MF104`; backfill first (`references/migrations.md`).
- `ALTER COLUMN` replaces the whole column definition, and drops a `NOT NULL` or `DEFAULT` it does not
  repeat. Atlas repeats them, so check hand-written `ALTER COLUMN` statements for the same.
- `allow_commit_timestamp = true` lets the column take `PENDING_COMMIT_TIMESTAMP()`. Turning it on for an
  existing column checks that its values are in the past
  (https://docs.cloud.google.com/spanner/docs/commit-timestamp).
- `STRING(MAX)` holds 2,621,440 characters and `BYTES(MAX)` 10,485,760 bytes. `NUMERIC` has precision 38
  and scale 9. A cell holds up to 10 MiB.
- Names hold 1 to 128 characters, and two names that differ only in case collide. Spanner reserves
  words such as `AT`, `NEW`, and `ALL`, which fail in a SQL schema with a `Syntax error` unless quoted with
  backticks. Atlas quotes every name it writes.

## Indexes

- Building an index on a populated table backfills it, which takes minutes to hours. Google advises at
  most 3 new backfilled indexes a day, and creating a table's indexes together with the table
  (https://docs.cloud.google.com/spanner/docs/schema-updates-best-practices#large-updates).
- A plain `UNIQUE` index treats `NULL`s as equal, so two rows with a `NULL` key collide. A
  `UNIQUE NULL_FILTERED` index skips rows with a `NULL` key part and does not enforce uniqueness for them
  (https://docs.cloud.google.com/spanner/docs/secondary-indexes#unique-indexes). Creating a unique index
  fails on duplicate rows (`MF101`).
- `STORING` columns change in place: Atlas plans `ALTER INDEX ... ADD STORED COLUMN` or
  `DROP STORED COLUMN`. Replacing one stored column with another fails planning with
  `cannot add and drop a column at the same time`: change one column per migration.
- An index's key columns cannot change: Atlas drops and recreates the index, which backfills again.
- Search indexes run over hidden `TOKENLIST` columns, and need the Enterprise edition. Vector indexes need
  a `vector_length` on the column, a `WHERE col IS NOT NULL` for a nullable column, and
  `distance_type` (https://docs.cloud.google.com/spanner/docs/vector-indexes). Declare vector indexes in
  HCL, and exclude them once created: `exclude = ["*.Docs.DocsEmbeddingIdx"]`. Inspection does not read
  their options back from the emulator, so later plans fail with
  `modify index "DocsEmbeddingIdx" must have at least one column to add or drop`.

## Foreign Keys

- Spanner backs each foreign key with indexes it manages, which inspection does not show. A foreign key
  takes `ON DELETE CASCADE` or `NO ACTION`.
- Adding a foreign key to a populated table checks every row, and the change fails on rows that break it
  (https://docs.cloud.google.com/spanner/docs/foreign-keys/overview).
- A changed foreign key is planned as `DROP CONSTRAINT` and `ADD CONSTRAINT` with the same name, which
  leaves the table unchecked until the new one validates. Google advises adding the new constraint
  before dropping the old one: rename it in the schema, and move the `ADD CONSTRAINT` above the
  `DROP CONSTRAINT` in the migration file.
- Informational foreign keys, `NOT ENFORCED`, are not validated or enforced. Atlas plans them as
  enforced, and inspects them as enforced. Create them in a hand-written migration file; declaring them
  the same way in a SQL schema then plans no change. The same holds for interleaved indexes.

## Checks, Generated Columns, and Defaults

- A check must be deterministic, and cannot read `allow_commit_timestamp` columns. Adding one checks
  every row and fails on rows that break it. Spanner cannot modify a check, so Atlas drops and re-adds it
  (https://docs.cloud.google.com/spanner/docs/check-constraint/how-to).
- A generated column uses only immutable functions. Adding a stored one backfills it, and it cannot be
  read until the backfill finishes. Spanner cannot change a stored or indexed generated expression, so
  Atlas drops and re-adds the column, which fails when an index uses it (What Atlas Leaves Out, above).
  A non-stored generated column cannot be `NOT NULL`
  (https://docs.cloud.google.com/spanner/docs/generated-column/how-to).
- A `DEFAULT` can be non-deterministic, such as `CURRENT_TIMESTAMP()` or `GENERATE_UUID()`, and cannot
  read other columns. A changed default is planned as `ALTER COLUMN` with the full definition and does
  not touch existing rows.

## Sequences

```sql
CREATE SEQUENCE OrderSeq OPTIONS (sequence_kind = 'bit_reversed_positive');
CREATE TABLE Orders (
  OrderId INT64 NOT NULL DEFAULT (GET_NEXT_SEQUENCE_VALUE(SEQUENCE OrderSeq)),
  Total NUMERIC,
) PRIMARY KEY (OrderId);
```

- `bit_reversed_positive` is the only kind. The values are unique and spread over the key space, not
  consecutive. `skip_range_min` and `skip_range_max` keep a range free, such as the ids an existing
  table already uses (https://docs.cloud.google.com/spanner/docs/primary-key-default-value).
- Atlas leaves identity columns out of plans, so use a named sequence and a `DEFAULT` instead of
  `GENERATED BY DEFAULT AS IDENTITY`. `AUTO_INCREMENT` and identity columns without a kind also need the
  `default_sequence_kind` database option, which Atlas does not manage and which cannot be changed once
  set.
- Option changes plan `ALTER SEQUENCE ... SET OPTIONS`.
- Spanner cannot drop a sequence that a column default or a view uses.

## Views

- Spanner requires `SQL SECURITY INVOKER` or `DEFINER` on every view; a SQL schema without it fails
  with ``View `V` is missing the SQL SECURITY clause``.
- A schema change that would break a view's query fails
  (https://docs.cloud.google.com/spanner/docs/schema-updates#validate-view-definitions).
- `CREATE OR REPLACE VIEW` drops the grants on the view, and Spanner does not restore them
  (https://docs.cloud.google.com/spanner/docs/create-manage-views). With permissions managed, plan again
  after a view change to grant them back.
- Views are read-only and cannot be indexed.

## Change Streams

- Atlas plans any change to a stream as `DROP CHANGE STREAM` and `CREATE CHANGE STREAM`. Dropping a
  stream deletes its change records, and readers of the old stream stop
  (https://docs.cloud.google.com/spanner/docs/change-streams/manage). Change a stream in a hand-written
  migration file, and the schema then plans no change:

  ```sql
  ALTER CHANGE STREAM EventsStream SET OPTIONS (retention_period = '3d');
  ALTER CHANGE STREAM SingersBio SET FOR Singers(Name);
  ```

  The `statement` rule in `references/migrations.md` flags a planned `DROP CHANGE STREAM`.
- `retention_period` runs from `1d` to `30d`, 7 days by default. A database holds up to 10 streams, and
  a column can be watched by up to 3 (https://docs.cloud.google.com/spanner/quotas).
- Spanner refuses to drop a table or column that a stream watches by name. Atlas changes the stream
  first, by recreating it.

## Row Deletion Policies

- `ROW DELETION POLICY (OLDER_THAN(CreatedAt, INTERVAL 30 DAY))` deletes rows once the `TIMESTAMP`
  column is older than the interval, usually within 72 hours. Rows with a `NULL` timestamp stay
  (https://docs.cloud.google.com/spanner/docs/ttl).
- A table holds one policy. Atlas plans `ADD`, `REPLACE`, or `DROP ROW DELETION POLICY`.
- All interleaved children of the table need `ON DELETE CASCADE`, and every foreign key that references
  it needs `ON DELETE CASCADE`. Spanner refuses to drop the policy's column
  (https://docs.cloud.google.com/spanner/docs/ttl/working-with-ttl).

## Named Schemas

- `CREATE SCHEMA sales` holds tables, views, indexes, foreign keys, and sequences, referenced by their
  qualified names (`sales.Orders`). An index lives in its table's schema, and a schema cannot be dropped
  while it holds objects (https://docs.cloud.google.com/spanner/docs/named-schemas).
- The default schema is `default` in GoogleSQL HCL and `public` in the PostgreSQL dialect.
- Keep sequences in the default schema (What Atlas Leaves Out, above).

## Enterprise Features

| Feature | Edition | Atlas |
|---------|---------|-------|
| Search indexes, vector indexes, property graphs | Enterprise or Enterprise Plus | Planned. Vector index options need HCL |
| Locality groups (tiered storage) | Enterprise or Enterprise Plus | Planned from HCL. The emulator keeps only some of their options |
| Placements (geo-partitioning, Preview) | Enterprise Plus | Planned from HCL. The emulator treats them as no-ops |

The edition table is https://docs.cloud.google.com/spanner/docs/editions-overview. A placement cannot
be altered, and a placement key cannot be added to an existing table
(https://docs.cloud.google.com/spanner/docs/create-manage-data-placements). Spanner Graph is GoogleSQL
only.

## PostgreSQL Dialect

A database's dialect is fixed when the database is created. Atlas reads it from the target; plan
PostgreSQL-dialect databases on `docker://spannerpg/<version>` (`references/dev-database.md`).

What Spanner's PostgreSQL interface leaves out
(https://docs.cloud.google.com/spanner/docs/reference/postgresql/overview,
https://docs.cloud.google.com/spanner/docs/reference/postgresql/data-types):

- No triggers, stored functions, extensions, enums, or user-defined types.
- `int` is `bigint`, and `char` and `timestamp without time zone` do not exist.
- `numeric`, `float4`, and `jsonb` columns cannot be keys or be indexed: an index on one fails with
  `Cannot reference PG.NUMERIC total in the creation of index`.
- A numeric default needs a cast, `DEFAULT 0::numeric`. Without it the schema fails with
  `Expected type PG.NUMERIC; found INT64`.
- Partial indexes accept only `WHERE col IS NOT NULL`.

Atlas on the PostgreSQL dialect:

| Object | What happens | What to do |
|--------|--------------|------------|
| `TTL INTERVAL '30 days' ON created_at` | In the schema or in a migration file, planning fails: `is not supported in Spanner PostgreSQL dialect`. Added by hand on the target, the next declarative plan drops it | Keep TTL tables out of Atlas with `exclude`, and manage their TTL by hand |
| `spanner.commit_timestamp` columns | The first plan works; every later plan fails with `unsupported type` | Declarative: exclude the columns, `exclude = ["*.*.updated_at"]`. Versioned: `migrate diff` cannot plan again, and the same `exclude` plans a `DROP COLUMN` for them |

Tables, interleaving, indexes with `INCLUDE`, checks, stored generated columns, `jsonb` columns,
sequences with `nextval('seq')` defaults, and `SQL SECURITY INVOKER` views plan and round-trip.
