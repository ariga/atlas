# Oracle Objects and Their Nuances

How Atlas models Oracle objects, and the cases where its plan differs from what a hand-written migration
would do. The full attribute reference is https://atlasgo.io/hcl/oracle. HCL syntax is in
`references/hcl.md`, and locks, lint, and migration files are in `references/migrations.md`.

## What Atlas Manages

The whole Oracle driver needs `atlas login`: logged out, every command that connects to Oracle aborts
with `The oracle driver is available only to Atlas Pro users`. If `atlas whoami` shows no login, ask the
user to run `atlas login`; a user without an account can start a free trial with it.

Atlas inspects and plans tables and columns, primary keys, unique and check constraints, foreign keys,
indexes, comments, views, sequences, functions, procedures, triggers, object types, varrays, nested
tables, synonyms, database links, operators, index types, roles, and object grants
(https://atlasgo.io/hcl/oracle).

These are left out of plans without an error, so a plan that reports no changes can still be missing
them:

| Object or clause | What happens | What to do |
|------------------|--------------|------------|
| Packages and package bodies | Left out of plans; inspection does not list them, and plans never drop them | Create them in hand-written migration files (`references/migrations.md`) |
| `PARTITION BY` | Left out of the planned `CREATE TABLE`; a partitioned table on the target inspects as a plain table, and plans leave its partitions alone | Create partitioned tables in hand-written migration files |
| `INVISIBLE` columns | Planned as visible columns | Set it in a hand-written migration file |
| A check whose whole expression is `col IS NOT NULL` | Left out, named or not: Oracle records `NOT NULL` constraints in the same form | Declare the column `null = false` (`NOT NULL`) |
| `START WITH` of a sequence | Not planned; the sequence starts at its `MINVALUE` | Sequences and Identity Columns below |
| Renames | No `renamed_from` on Oracle: planned as a drop and an add | Rename by hand (`references/migrations.md`, Renames) |
| PL/SQL that does not compile | Left out of plans | PL/SQL below |
| Users, grants of roles to users, system privileges, schema privileges | Not inspected or planned | `references/security.md` |
| Materialized views | Break planning, and inspect as tables | Views and Materialized Views below |

## Names

- Oracle folds unquoted names to uppercase and keeps quoted names as written
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/Database-Object-Names-and-Qualifiers.html).
  Atlas quotes every name it writes:
  - In a SQL schema, unquoted names become uppercase: `CREATE TABLE users` plans `CREATE TABLE "USERS"`.
  - In HCL, the label is the name: `table "users"` creates the lowercase table `"users"`, which every
    query must then quote (`SELECT "id" FROM "users"`). Write HCL labels in uppercase.
  - Plan comments print names in lowercase (`add new table named "orders"`); the statements use the
    real name.
- Names can be 128 bytes long when `COMPATIBLE` is 12.2 or higher, and 30 bytes before. A longer name
  fails with `ORA-00972: identifier is too long`.
- Index names and constraint names are each unique within a schema, not within a table. Two tables
  cannot both have an index named `IDX_STATUS` (`ORA-00955: name is already used by an existing object`)
  or a constraint named `PK` (`ORA-02264`). Tables and indexes are separate namespaces, so an index can
  share its table's name.

## Constraint Names

Oracle names an unnamed constraint `SYS_C` followed by a number. For an unnamed primary key, unique
constraint, or foreign key in a SQL desired state, Atlas copies the name the dev database generated into
the plan:

```sql
CREATE TABLE "ORDERS" (
  "ID" NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY,
  "CUSTOMER_ID" NUMBER NOT NULL,
  CONSTRAINT "SYS_C008556" PRIMARY KEY ("ID"),
  CONSTRAINT "SYS_C008557" FOREIGN KEY ("CUSTOMER_ID") REFERENCES "CUSTOMERS" ("ID") ON DELETE CASCADE
)
```

- The copied name can belong to another constraint on the target, and the statement fails with
  `ORA-02264: name already used by an existing constraint`.
- The numbers shift when the desired state changes, for example when a table with unnamed constraints is
  added above. The plan then fails with
  `the planned state does not match the desired state after applying the file`. With
  `diff { skip { rename_constraint = true } }`, it drops and re-adds the foreign key instead, which
  checks every row again.
- Name every primary key, unique constraint, and foreign key: `CONSTRAINT orders_pk PRIMARY KEY (id)`.
  HCL requires these names. Name checks too; an unnamed check is planned without a name and stays
  stable.
- For constraints that already exist, keep the `SYS_C` names that `atlas schema inspect` writes, such as
  `primary_key "SYS_C008556"`.

## Numbers, Strings, and Dates

- `INTEGER`, `INT`, `SMALLINT`, and `NUMBER(*,0)` are `NUMBER` with scale 0. Atlas plans them as plain
  `NUMBER`, which accepts decimals, and later plans do not report the difference. Write integers with a
  precision: `NUMBER(10)`, `NUMBER(19)`, or `NUMBER(38)`.
- Oracle treats `''` as `NULL` (https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/Nulls.html):
  - A `NOT NULL` `VARCHAR2` column rejects `''` with `ORA-01400`.
  - `DEFAULT ''` is no default.
  - `WHERE col = ''` matches no rows.
  - A backfill of `SET col = ''` before `MODIFY col NOT NULL` leaves the rows `NULL`, and the change
    fails with `ORA-02296: cannot enable (...) - null values found`. Backfill a real value
    (`references/testing.md`).
- A `VARCHAR2` length counts bytes unless it says `CHAR` (`NLS_LENGTH_SEMANTICS`): `VARCHAR2(100)` holds
  fewer than 100 characters of multibyte text. Write `VARCHAR2(100 CHAR)` for a character length. Atlas
  keeps the qualifier, and inspection writes it as `sql("VARCHAR2(100 CHAR)")`.
- `VARCHAR2` holds up to 4000 bytes, or 32767 with `MAX_STRING_SIZE = EXTENDED`
  (`references/dev-database.md`). Use `CLOB` for longer text.
- `DATE` stores a time, to the second. `TIMESTAMP` has 6 fractional digits by default and inspects as
  `sql("TIMESTAMP(6)")`. `FLOAT` is a `NUMBER` with binary precision and inspects as `FLOAT(126)`.
- `BOOLEAN` (23ai), `JSON` (21c), and `VECTOR` (23.4) exist only on those releases: on an older target,
  see `references/dev-database.md`, Versions and Settings. `VECTOR` columns are covered in
  https://atlasgo.io/guides/oracle/vector.
- `LONG` columns are deprecated and limited to one per table. Convert them to `CLOB`.

## Sequences and Identity Columns

- Atlas does not plan a sequence's start: `START WITH` in SQL and `start` in HCL are both dropped, and
  the sequence starts at its `MINVALUE`, 1 by default. Oracle's dictionary does not record the start
  value, so later plans never report it. Set the start outside the plan:
  - Versioned: write it in the migration file, `CREATE SEQUENCE "INVOICE_SEQ" START WITH 50000;`, and
    declare the sequence without a start. `migrate diff` stays in sync.
  - Declarative: declare the sequence without a start, apply it, then move it once by hand:
    `ALTER SEQUENCE "INVOICE_SEQ" RESTART START WITH 50000;`
    (https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/ALTER-SEQUENCE.html). Later
    plans leave it alone.
- Never set `min_value` to get a start value. Atlas plans `START WITH 50000 MINVALUE 50000`, and once the
  sequence has handed out numbers, every later declarative plan adds
  `ALTER SEQUENCE "INVOICE_SEQ" RESTART START WITH 50000`, which moves it back and repeats numbers. Check
  every plan for `ALTER SEQUENCE ... RESTART` before applying it.
- An identity column's `start` is planned, and plans leave the identity alone once rows use it.
- Identity columns take `GENERATED ALWAYS`, the default, `BY DEFAULT`, or `BY DEFAULT ON NULL`
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/CREATE-TABLE.html):
  - A table has at most one, and it is implicitly `NOT NULL`.
  - `ALWAYS` rejects explicit values with `ORA-32795`, which blocks backfills and table copies. Use
    `BY DEFAULT` for columns that receive copied rows, then move the generator past them with
    `ALTER TABLE "T" MODIFY "ID" GENERATED BY DEFAULT AS IDENTITY (START WITH LIMIT VALUE);`.
  - An existing column cannot become an identity column (`ORA-30673`): add a new one.
  - Inspection hides the `ISEQ$$_` sequence behind each identity column, and writes `identity {}` for
    `ALWAYS`, or `identity { generated = BY_DEFAULT, on_null = INSERT_ONLY }`.
- Seed rows in a `data` block skip `GENERATED ALWAYS` identity values even with `preserve_ids = true`;
  `BY DEFAULT` values are kept with it
  (https://atlasgo.io/atlas-schema/hcl#preserving-explicit-ids).

## Keys, Constraints, and Indexes

- A foreign key's `on_delete` takes `NO_ACTION`, `CASCADE`, or `SET_NULL`. Oracle has no `ON UPDATE`
  action.
- Index the columns of every foreign key. Without an index, updating a parent key or deleting a parent
  row locks the whole child table, and Oracle's guidance is that "foreign keys should almost always be
  indexed"
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/data-concurrency-and-consistency.html).
  Atlas creates no index on its own; enforce it with the rule in `references/custom-rules.md`.
- Constraint states, on primary keys and unique constraints: `validated = false` is `NOVALIDATE`, where
  existing rows are not checked but new rows are, plus `enabled`, `rely`, and `deferrable`.
  - A primary key or unique constraint needs an index, and Oracle builds a unique one when the constraint
    has none, even with `NOVALIDATE`. On a table with duplicate values, the plain plan fails with
    `ORA-02299: cannot validate (...) - duplicate keys found`. Declare a non-unique index and point the
    constraint at it (`references/hcl.md`, Keys, Constraints, and Indexes).
  - Foreign keys and checks have no `validated` attribute. Add those `NOVALIDATE` in a hand-written
    migration file (`references/migrations.md`, Locks and Online Changes).
- Index options: `unique`, `bitmap`, `reversed` (a reverse key index), `on` blocks with `expr` for
  function-based indexes and `desc` for descending parts, `domain` and `parameters` for domain indexes,
  and `physical` for the tablespace and storage. Oracle stores a descending part as an expression, so
  inspection writes `on { desc = true, expr = "\"PLACED_AT\"" }`.
- The lite dev image has only the `BASIC_LEXER` for Oracle Text, so `CTXSYS.CONTEXT` domain indexes with
  other lexers need the full image (`references/dev-database.md`).
- Atlas plans `CREATE INDEX` without `ONLINE`, which blocks writes to the table while the index builds;
  see `references/migrations.md`.

## PL/SQL: Functions, Procedures, and Triggers

- A `function` takes `arg` blocks with `type`, `mode` (`IN`, `OUT`, `INOUT`), `default`, and `nocopy`,
  a `return` type, `deterministic`, and its body in `as`. A `procedure` takes the same without a return.
  Types can be schema types, `sql("...")`, or references to object types, varrays, and nested tables.
- A function, procedure, or trigger that does not compile on the dev database is left out of the plan,
  and out of `migrate diff`, without an error. Oracle still creates it, as `INVALID`, and Atlas does not
  load invalid objects. Compare the plan with the schema, and test every routine
  (`references/testing.md`).
- In a migration file, Oracle creates PL/SQL with compilation errors as `INVALID`, and Atlas reports the
  statement as applied. An invalid trigger fails every statement that fires it, with
  `ORA-04098: trigger '...' is invalid and failed re-validation`, until it is fixed
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/lnpls/trigger-compilation-invalidation-and-recompilation.html).
  A migration test that checks for invalid objects catches it before a deployment does
  (`references/testing.md`).
- A trigger takes one of `before`, `after`, or `instead_of` (for views), `for = ROW` or `STATEMENT`,
  optional `referencing`, `when`, `follows` or `precedes`, and its body in `as`. The body reads
  `:NEW` and `:OLD`, but a `when` condition writes `NEW` and `OLD` without the colon
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/lnpls/CREATE-TRIGGER-statement.html).
- Definer's-rights code and views run without the owner's roles: privileges they use must be granted to
  the owner directly (`references/security.md`).
- DDL on a table makes dependent views and PL/SQL `INVALID` until their next use recompiles them, and
  sessions running that code can fail with `ORA-04068`. After a deployment, recompile with
  `UTL_RECOMP` or `DBMS_UTILITY.COMPILE_SCHEMA`
  (https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-schema-objects.html).

## Views and Materialized Views

- A `view` takes `as`, `depends_on`, and `column` blocks. Atlas plans it with a column list:
  `CREATE VIEW "VIP_CUSTOMERS" ("ID", "EMAIL") AS SELECT ...`.
- Atlas does not manage materialized views:
  - A `CREATE MATERIALIZED VIEW` in the desired state breaks planning:
    `ORA-12083: must use DROP MATERIALIZED VIEW to drop "PDBADMIN"."EVENTS_MV"`.
  - A materialized view on the target inspects as a `table` block, and a desired state without it plans
    `DROP TABLE` for it.
  - Exclude materialized views by name (`exclude = ["EVENTS_MV"]`), and create them in hand-written
    migration files.

## Other Objects

- Object types (`object_type`, with attributes, methods, constructors, `under` and `final`), `varray`,
  and `nested_table` can type columns and arguments.
- `synonym` points at a table, view, sequence, function, or procedure, or a name through a
  `database_link`. A `database_link` takes a `host` and its credentials; keep passwords in input
  variables (https://atlasgo.io/atlas-schema/input-variables).
- `operator` and `index_type` model Data Cartridge objects for domain indexes.
