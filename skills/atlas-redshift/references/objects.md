# Redshift Objects and Their Nuances

How Atlas models Redshift objects, and the cases where its plan differs from what a hand-written
migration would do. The full attribute reference is https://atlasgo.io/hcl/redshift, and the HCL
details are in `references/hcl.md`.

## What Needs a Login

Every Redshift command needs `atlas login`, so nothing is skipped silently when logged out: the command
fails with `login is required to use the 'redshift' driver`. If `atlas whoami` shows no login, ask the
user to run `atlas login`; a user without an account can start a free trial with it. Logged in, Atlas
manages:

- Schemas and their comments, and external schemas (`external` block)
- Tables: columns, comments, `encode`, `identity`, `distribution`, `sort`
- Views, late-binding views, and materialized views
- SQL functions and PL/pgSQL procedures, with overloads
- Users, groups, roles, and memberships (`roles = true`), and grants (`permissions = true`)
- Datashares created in the database (`mode "redshift" { datashares = true }`)

What Atlas leaves out is listed in Not Managed by Atlas, at the end of this file.

## Distribution, Sort Keys, and Encodings

- `distribution` takes `style` (`AUTO`, `EVEN`, `ALL`, `KEY`) and, for `KEY`, `column`. A block with
  only `column` means `KEY`. Without a block, the table gets `DISTSTYLE AUTO`.
- `sort` takes `style` (`AUTO`, `COMPOUND`, `INTERLEAVED`) and `columns`. Columns without a style mean
  `COMPOUND`. Without a block, the table gets `SORTKEY AUTO`. Redshift gives an interleaved table
  `DISTSTYLE EVEN` unless the state sets another style.
- Inspection always writes both blocks, and `encode` on every column, the way Redshift reports them.
- Changing a style or key on an existing table is an `ALTER`:

  ```sql
  ALTER TABLE "t2" ALTER DISTSTYLE KEY DISTKEY "c1";
  ALTER TABLE "t3" ALTER DISTSTYLE EVEN;
  ALTER TABLE "t6" ALTER SORTKEY ("c1", "c2");
  ```

  These run inside a transaction. Changing to an `INTERLEAVED` sort key fails with
  `modify sort key to INTERLEAVED is not supported in Redshift`: Redshift sets one only in
  `CREATE TABLE`, so rebuild the table in a hand-written migration (create, copy, drop, rename).
  Leaving an interleaved key is planned, without a reverse for `atlas migrate down`.
- Atlas cannot plan the removal of a distribution style or a sort key:
  `dropping the distribution style of table "t" is not supported`, or
  `dropping the sort key of table "t" is not supported`. With a dev database, a table without the
  blocks normalizes to `AUTO`; to go back to the default, set `style = AUTO`.
- A column without `encode` gets the encoding Redshift picks: `AZ64` for integers, numerics, dates,
  times, and timestamps, `LZO` for character and `varbyte` columns, `ZSTD` for `super`, and `RAW` for
  sort key columns, `boolean`, `real`, `double precision`, intervals, `hllsketch`, and spatial types.
  Changing `encode` later is `ALTER TABLE ... ALTER COLUMN "c" ENCODE <type>`, inside a transaction.

## Identity Columns

- `identity { generated = ALWAYS }` or `BY_DEFAULT` (the default), with `seed` and `step`, both 1 by
  default. An explicit `seed = 0` is kept.

  ```sql
  "c1" integer NOT NULL GENERATED BY DEFAULT AS IDENTITY(1, 1) ENCODE AZ64
  ```

- An identity column exists only from `CREATE TABLE`. Adding one fails with
  `adding identity column "c" is not supported after the table is created`; changing its seed, step, or
  generation, or removing it, fails with `modify column identity is not supported in Redshift`. Create a
  new table with the identity and copy the rows in a hand-written migration.

## Column Changes

Redshift alters few column properties in place. What Atlas plans for each change:

| Change | Plan |
|--------|------|
| Comment | `COMMENT ON COLUMN` |
| `encode` | `ALTER COLUMN "c" ENCODE <type>` |
| Type, on a column with no default and an encoding other than `BYTEDICT`, `RUNLENGTH`, `TEXT255`, `TEXT32K` | `ALTER COLUMN "c" TYPE <type>`, outside a transaction |
| Type, on a column with a default or one of those encodings | Refused: `Column "c" type change requires recreating the column` |
| Default | Refused: `Column "c" default change requires recreating the column` |
| Nullability | Refused: `Column "c" nullability change requires recreating the column` |
| Identity | Refused: `modify column identity is not supported in Redshift` |
| New column | `ADD COLUMN`; a `NOT NULL` one needs a `default`, or fails with `adding non-nullable column "c" requires a default value in Redshift` |

- Redshift's `ALTER COLUMN ... TYPE` changes only the length of a `varchar` column. Atlas still plans it
  for other type changes, such as `integer` to `bigint`, and Redshift rejects it when applied. Write
  those by hand: add a column with the new type, copy the values with `UPDATE`, drop the old column, and
  rename the new one. Test it with seeded rows (`references/testing.md`).
- `ALTER COLUMN ... TYPE` cannot run in a transaction, so the generated file starts with
  `-- atlas:txmode none` (`references/migrations.md`).

### Rebuilding a column: `allow_recreate`

A refused change ends with
`Set 'allow_recreate' in the 'modify_column' block of the diff policy to plan it`. With the policy,
Atlas drops the column and adds it back:

```hcl
env "dev" {
  diff "redshift" {
    modify_column {
      allow_recreate = true
    }
  }
}
```

```sql
-- Drop column "c1" on table: "t1" for recreation
ALTER TABLE "t1" DROP COLUMN "c1";
-- Add column "c1" on table: "t1" as replacement
ALTER TABLE "t1" ADD COLUMN "c1" character varying(200) NOT NULL DEFAULT 'test' ENCODE LZO;
```

- The values are lost: every row gets the new default, or `NULL`. The column moves to the end of the
  table, and its comment and grants are planned again after it. The rebuild has no reverse for
  `atlas migrate down`.
- Without the policy, an interactive run asks before rebuilding, with the choices `Abort` and
  `Drop and recreate column "c" (data loss)`. A run without a terminal, as in CI, fails.
- `atlas schema apply` lints the plan it generates, so the env it runs with needs the same policy.
- Some columns cannot be rebuilt, and the error says why after the reason:
  `..., but a non-nullable column requires a default value in Redshift`,
  `..., but it is the distribution key of table "t"`,
  `..., but it is part of the sort key of table "t"`,
  `..., but it is the only column of table "t"`, and
  `..., but an identity column cannot be added to an existing table`.
- To keep the data, write the migration by hand instead: add the new column, copy the values, drop the
  old one, and rename.

## Views and Materialized Views

- A changed view definition is `CREATE OR REPLACE VIEW`. A change to the view's column count, names,
  or types is a `DROP VIEW` and a `CREATE VIEW`. Atlas writes the column list:
  `CREATE VIEW "v1" ("c1") AS ...`.
- Late-binding views keep the clause in their definition:
  `as = "SELECT id FROM sales.orders WITH NO SCHEMA BINDING;"`. They are `view` blocks.
- A `materialized` view takes `distribution` (`EVEN`, `ALL`, `KEY`; `EVEN` when omitted), `sort`
  (`COMPOUND` only), and `auto_refresh`. Changing `auto_refresh` is
  `ALTER MATERIALIZED VIEW ... AUTO REFRESH YES`; changing its definition drops and recreates it, so
  Redshift computes it again from scratch.
- A view cannot turn into a materialized view or back: `cannot modify view "v" to materialized view`.
  Drop it in one migration and create it in the next.
- Dropping uses the kind's statement: `DROP VIEW` or `DROP MATERIALIZED VIEW`.

## Functions and Procedures

- Functions are SQL UDFs: `lang = SQL`, a `return` type, and `volatility` (`VOLATILE`, `STABLE`,
  `IMMUTABLE`). Procedures are `lang = PLpgSQL`, take arguments with `mode` (`IN`, `OUT`, `INOUT`) and
  `security` (`INVOKER`, `DEFINER`).
- Overloads are separate blocks with the same name. A changed body or volatility is
  `CREATE OR REPLACE`; a changed argument list or argument mode is a drop of the exact signature and a
  create:

  ```sql
  DROP PROCEDURE "get_value" ("result" OUT integer);
  CREATE PROCEDURE "get_value" ("result" INOUT integer) AS $$BEGIN result := result + 100; END;$$ LANGUAGE plpgsql;
  ```

- Python UDFs (`plpythonu`) are not inspected; Atlas neither plans nor drops them.
- With `permissions = true`, a new function gets `REVOKE EXECUTE ... FROM PUBLIC` unless the state
  declares the grant (`references/security.md`).

## External Schemas

An `external` block makes the schema external; its label is the source (`references/hcl.md`):
`data_catalog`, `hive_metastore`, `postgres`, `mysql`, `redshift`, `kinesis`, `msk`, or `kafka`.

```hcl
schema "es_kafka" {
  external "kafka" {
    uri            = "b-1.kafka.example.internal:9092"
    authentication = NONE
  }
}
```

- Redshift cannot alter an external schema, so any change to its source or options is
  `DROP SCHEMA "es" CASCADE` and `CREATE EXTERNAL SCHEMA`. Removing the `external` block turns it into a
  local schema the same way. Dropping an external schema unregisters it; the source is untouched.
- Its tables come from the source: a table, view, function, or procedure declared in it fails with
  `cannot create table "t1" in external schema "es_kafka"`.
- `CREATE EXTERNAL TABLE` and other external table DDL cannot run in a transaction; hand-written files
  need `-- atlas:txmode none`.
- Inspection reads an external schema as external only when the connecting user owns it or is a
  superuser: Redshift shows other users' external schemas as plain schemas. Declared with an `external`
  block, such a schema is planned for `DROP SCHEMA ... CASCADE` and `CREATE EXTERNAL SCHEMA` on every
  run. Run Atlas as the owner, or leave the schema out with `exclude`.

## Datashares

Datashares created in the database are managed at database scope with
`mode "redshift" { datashares = true }` in the env's `schema` block. Datashare names are unique per
cluster, so the dev database must be on a separate cluster or workgroup.

```hcl
datashare "orders_share" {
  accounts = ["000000000000"]
  schema {
    for     = schema.sales
    objects = [table.orders, table.audit, function.calc]
  }
}
```

- A `schema` block names the shared set one way: `objects`, `include_new = true` (every object, and
  the ones created later), or `include_new_except = [...]` (every object but these). `INCLUDENEW`
  shares only objects created after it is set, so Atlas adds the existing ones itself.
- Consumers go in `namespaces` (same account) or `accounts` (another account); one is required.
  `public_accessible` sets `PUBLICACCESSIBLE`.
- A function is shared by name: every overload is added and removed together.
- `GRANT USAGE ON DATASHARE`, `REVOKE USAGE ON DATASHARE`, and
  `ALTER DATASHARE ... SET PUBLICACCESSIBLE` on an existing share cannot run in a transaction; files
  that plan them start with `-- atlas:txmode none`.
- An env that manages a share over schemas owned by another pipeline sets `schemas = false` and names
  the schemas and objects as strings: `for = "ingest"`, `objects = ["raw_events"]`.
  Do not add a stub `schema` block for such a schema instead: Atlas compares the share with it, and
  plans to recreate the schema or to remove the share's objects.
- Removing a shared table plans its `REMOVE TABLE` before its `DROP TABLE`, and removing a schema from a
  share removes its objects first. Dropping the share revokes its consumers' access with it.

## Not Managed by Atlas

Atlas does not manage the following, and never plans changes to them. When the schema depends on one,
such as a Python UDF that a view calls, create it in the dev `baseline` (`references/dev-database.md`):

- Primary keys, foreign keys, and unique and check constraints. Redshift accepts `PRIMARY KEY`,
  `REFERENCES`, and `UNIQUE` as informational constraints it does not enforce. Inspection does not read
  them, so a SQL schema that declares them never plans them, and HCL has no blocks for them:
  `primary_key` fails with `unknown block type primary_key`. Declare the constraints Redshift's planner
  should see in a hand-written migration, if at all.
- Indexes, which Redshift does not have, and sequences, triggers, extensions, enums, and domains.
- Python UDFs (`plpythonu`), which inspection skips.
- Tables of an external schema, which belong to its source.
- Datashares received from another namespace, and datashares of another database on the cluster.
- Grants on the database itself, and grants scoped to every schema of the database
  (`GRANT ... FOR SCHEMAS IN DATABASE`).
- System schemas (`pg_catalog`, `information_schema`, `catalog_history`, `pg_automv`, `pg_auto_copy`,
  `pg_internal`, `pg_s3`, `pg_toast`, `pg_mv`, and temporary schemas), the `mv_tbl__*` tables that back
  materialized views, and the internal `mv_sp__*` procedures.
