# Credentials, URL Scope, and Tokens

Every resource needs the URL of its target database, and Atlas Pro features need an Atlas Cloud bot token
(https://atlasgo.io/integrations/kubernetes/declarative#credentials). Both live in Kubernetes Secrets.

## The Target URL

Store the URL in a Secret and reference it with `urlFrom`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: postgres-credentials
type: Opaque
stringData:
  url: "postgres://postgres:pass@postgres.default:5432/postgres?sslmode=disable&search_path=public"
```

```yaml
apiVersion: db.atlasgo.io/v1alpha1
kind: AtlasSchema
metadata:
  name: atlasschema-pg
spec:
  urlFrom:
    secretKeyRef:
      key: url
      name: postgres-credentials
  schema:
    sql: |
      create table t1 (
        id int
      );
```

Or create the Secret from the command line, which keeps the URL out of manifest files:

```bash
kubectl create secret generic postgres-credentials \
  --from-literal=url="postgres://postgres:pass@postgres.default:5432/postgres?sslmode=disable&search_path=public"
```

- The password belongs to the user: ask them to create the Secret, and never print or echo it.
- The Secret must be in the same namespace as the resource.
- `url` takes the URL inline. It puts the password in the manifest; use it only for testing.
- The operator connects from its own pod. An in-cluster database needs its namespace-qualified service
  name, such as `postgres.default` or `mysql.app`: a short name resolves in the operator's namespace, and
  `localhost` is the operator itself.
- Special characters in the password must be URL-encoded (https://atlasgo.io/faq/url-special-chars).
- A Secret key that does not exist reads as an empty URL. The error then names an empty driver, such as
  `unknown driver for schema ""`: check the Secret's key.

### The credentials block

`credentials` builds the URL from parts, with the password from a Secret:

```yaml
apiVersion: db.atlasgo.io/v1alpha1
kind: AtlasSchema
metadata:
  name: atlasschema-postgres
spec:
  credentials:
    scheme: postgres
    host: postgres.default
    user: root
    passwordFrom:
      secretKeyRef:
        key: password
        name: postgres-credentials
    database: postgres
    port: 5432
    parameters:
      sslmode: disable
  # ... rest of the resource
```

`hostFrom` and `userFrom` read the host and user from Secrets too, which fits Secrets generated by other
tools. When `urlFrom` is set, `url` and `credentials` are ignored.

## URL Scope

The URL decides what Atlas manages (https://atlasgo.io/concepts/url#scope):

| URL | Scope | Atlas manages |
|-----|-------|---------------|
| `postgres://user:pass@your.db.com:5432/?search_path=myapp&sslmode=disable` | Schema | The `myapp` schema, with unqualified DDL |
| `postgres://user:pass@your.db.com:5432/?sslmode=disable` | Database | Every schema, with qualified DDL |
| `mysql://user:pass@your.db.dns.default:3306/myapp` | Schema | The `myapp` database |
| `mysql://user:pass@your.db.com:3306/` | Server | Every database |

- Use a database-scoped URL when the schema uses qualified names (`myschema.myfunc()`), spans several
  schemas, or declares extensions or roles. A mismatch fails with errors such as `already exists`, or
  plans the wrong changes.
- `AtlasSchema.schemas` lists the schemas to manage, and works only with a database-scoped URL.
- The dev database the operator creates follows the target's scope. A `devURL` you provide must have the
  same scope (`references/dev-database.md`).
- On PostgreSQL, a schema-scoped URL keeps the migration history table in that schema; a database-scoped
  URL keeps it in its own `atlas_schema_revisions` schema (`references/versioned.md`).

## The Atlas Cloud Bot Token

The operator runs in the cluster and authenticates with a bot token, not with a user's `atlas login`
session (https://atlasgo.io/cloud/bots). A user without an Atlas account starts a free trial with
`atlas login`.

1. In Atlas Cloud, as an admin, open the menu, then Settings > Bots > Create Bot. Copy the token: it is
   shown once.
2. Ask the user to store it in a Secret in the resource's namespace:

   ```shell
   kubectl create secret generic atlas-token --from-literal=token=<your token here>
   ```

3. Reference it from each resource:

   ```yaml
     cloud:
       tokenFrom:
         secretKeyRef:
           name: atlas-token
           key: token
   ```

- `name` is the Secret and `key` is its data key. Keep both the same in every resource; swapping them,
  or a key the Secret does not have, fails the login.
- `AtlasSchema`, `AtlasMigration`, and `AtlasSecurityScan` take `cloud.tokenFrom`. An `AtlasDriftCheck`
  uses the token of the `AtlasMigration` it checks.
- The `cloud` block differs by kind: `AtlasSchema` also takes `repo`, the registry repository for its
  plans (`references/declarative.md`), and `AtlasMigration` takes `project`. `cloud.repo` is not a field
  of `AtlasMigration`.
- Enable the chart's `persistence`. The operator caches the token's grant on it, which keeps Pro
  features working when Atlas Cloud is unreachable, across operator restarts (`references/install.md`).

### What needs the token

| Feature | Without a token |
|---------|-----------------|
| Registry sources: `schema.url: atlas://...`, `dir.remote` | Rejected: `dir.remote` fails with `cannot use remote directory without Atlas Cloud token` |
| Views, triggers, functions, procedures, sequences, extensions, and other objects beyond tables and indexes | Not managed, or the desired state fails on the dev database |
| SQL Server, ClickHouse, and Redshift drivers | `login is required to use ...` |
| `policy.lint.review`, pre-approved and ad-hoc plans | `auto-approve is not allowed when a lint policy is set to "ERROR"` |
| Custom configuration (`config`, `configFrom`) | `command requires 'atlas login'`, or `login is required to use custom atlas.hcl config` |
| `policy.drift`, `AtlasDriftCheck`, `AtlasSecurityScan` | The check or scan fails |
| Down migrations with approval | Registry directories only, which need the token |

An operator-wide token through the chart's `extraEnvs` covers the drivers and objects for every resource,
but a registry directory still needs `cloud.tokenFrom` (`references/install.md`).

## Cloud Sign-In Instead of Passwords

- AWS RDS and GCP Cloud SQL IAM authentication generate the password at connect time through custom
  configuration (`references/config.md`).
- The operator pod opens the connections, not the dev database pod. A cloud identity, such as an IAM
  role or a workload identity, belongs to the operator's service account, which the chart's values
  configure (https://github.com/ariga/atlas-operator/blob/master/charts/atlas-operator/values.yaml).
- For Azure SQL, Atlas reads the identity through the `fedauth` parameter, for example
  `azuresql://<instance>.database.windows.net?fedauth=ActiveDirectoryDefault&database=master`
  (https://atlasgo.io/concepts/url).
